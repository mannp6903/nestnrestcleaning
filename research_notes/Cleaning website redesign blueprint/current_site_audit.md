## 1. Architecture: how pages are generated, how config-driven content is, integrations, hosting constraints

### Takeaway
A zero-dependency Node script (tools/build.mjs, 2,654 lines) renders 38 static HTML files from one settings object (js/config.js) plus two content modules (guides, landmark SVG art); the browser re-reads the same config at runtime to compute prices and drive booking. Every integration (FormSubmit, Google Sheet, n8n, Cal.com, Easy!Appointments, Chatwoot, listmonk, GA4) is a config switch with build-time guards, and the site must stay static because it is served by GitHub Pages.

### Inferences
- The build is a single 200 KB template file with HTML in template literals; a redesign can either keep this generator (re-skin templates and CSS) or replace it, but must keep the config contract and both pricing implementations in sync (tests in tools/qa/v7 check this).
- Static hosting rules out server rendering, per-request personalisation, custom HTTP headers (CSP, cache-control, preload Link headers) and server-side form handling; all dynamic behaviour must be client-side JS or third-party endpoints.
- The absence of a bundler or real minifier means any heavy animation library would be shipped as an extra script tag; there is no tree-shaking or code-splitting today.

### Gaps
- GitHub Pages response headers (gzip/brotli, cache lifetimes) were not observed; local server had no compression.
- tools/sheet/Code.gs and the n8n workflows were not audited in depth.

## 2. Design system: colour, type, spacing, grid, components, iconography, illustration, logo, photography
